# Stage B Joint Rectangle Action Audit

Date: 2026-07-30

Audit target: check whether the current Stage B implementation matches the intended **Keypoint-Anchored Causal Rectangularization** method.

## Executive Conclusion

The current implementation **does not yet implement the formal joint rectangularization method**.

The current code is better described as:

```text
Fast/Dyna keypoint refresh
-> unconditional member-level causal delay actuator, if max_delay > 0
-> heterogeneous dummy insertion candidate exposure, capped by top-k
-> RF exact evaluation over dummy-only candidate TAMs
```

For prototype transfer, the current `P0+ + D64` result is best described as:

```text
member-level generic delay actuator
+ prototype normalized dummy replay
```

It is **not**:

```text
Teacher selection from 128 joint (span L, target height H) rectangularization candidates
where renderer jointly derives real-packet delay and dummy insertion.
```

## Formal Method Being Audited Against

The intended method should expose a candidate action approximately shaped as:

```text
a = (keypoint k, temporal span L, target height H)
```

A valid candidate should jointly derive:

```text
real packets delayed from high bins to later lower bins
dummy packets inserted into remaining low bins
actual bandwidth
average / p95 / maximum delay
rectangle shape error
RF gain
```

The intended Teacher score should be closer to:

```text
S(a) = RF_gain(a)
     - lambda_B * bandwidth(a)
     - lambda_D * delay(a)
     - lambda_R * rectangle_shape_error(a)
```

## Direct Answers

### 1. Does the current formal Teacher implement joint rectangularization?

No.

It implements keypoint-guided delay plus keypoint/structure-guided dummy insertion search. It does not expose a candidate action whose main variables are `(span L, target height H)`, and it does not make the renderer jointly derive delay and dummy for each candidate.

### 2. Does current delay participate in top128 Teacher selection?

No.

Delay is applied before top128 dummy candidate generation when `max_delay > 0`. The top128 candidates do not contain delay parameters, and candidate scoring does not include candidate-level delay penalty or rectangle shape error.

### 3. Is current P0+ + D64 just generic delay plus prototype dummy?

Yes.

More precisely:

```text
P0+ + D64 = member-level generic fast-keypoint delay actuator
          + prototype normalized dummy replay
```

The delay is computed per member trace, while dummy actions are transferred from cluster prototype policies.

### 4. What are the gaps from the formal method definition?

Main gaps:

```text
No keypoint_rectangularize action type.
No span_bins / target_height candidate variables.
No renderer that jointly moves real packets and inserts dummy according to an (L,H) rectangle target.
No candidate-level average/p95/max delay fields.
No rectangle shape error field.
No score of RF gain - bandwidth penalty - delay penalty - shape error.
Delay is outside top128, not part of each candidate.
top128 is an exposure cap over heterogeneous dummy descriptors, not a 128-cell rectangle grid.
Prototype transfer replays/scales dummy actions; it does not transfer joint rectangle policies.
```

## Recommended Next Step

Before P1, freeze the method definition and introduce a new candidate family:

```text
action_type = keypoint_rectangularize
fields:
  keypoint_rank
  direction
  anchor_bin
  span_bins
  target_height
  dummy_count_actual
  average_delay_bins
  p95_delay_bins
  maximum_delay_bins
  bandwidth_ratio
  shape_error
  estimated_gain
  exact_gain
```

The new renderer should take `(keypoint, L, H)` and produce one joint candidate state containing both causal packet delay and dummy insertion. Only after that should top128 mean “128 feasible local rectangularization candidates” or “top128 from a larger `(L,H)` grid.”
